# Техническое задание

# Модернизация сборочной системы ffmpeg_builder

## 1. Назначение

Разработать механизм постоянного хранения и использования инструментов сборки (toolchain), позволяющий выполнять сборку FFmpeg непосредственно на целевой системе без зависимости от состава и версий инструментов, установленных в хостовой операционной системе.

Основная цель проекта:

> Система должна собирать FFmpeg на хосте для хоста.

Постоянному хранению подлежат исключительно инструменты подготовки и сборки.

Результаты сборки FFmpeg, библиотеки FFmpeg и собранные зависимости не являются частью постоянного хранилища и всегда должны собираться заново под текущую целевую систему.

---

# 2. Причины модернизации

Первоначальная архитектура использовала проверку совместимости компилятора хостовой системы.

После появления поддержки FFmpeg 9.0 были добавлены профили совместимости, однако они фактически представляли собой признак:

```text
allowed / not allowed
```

Позже была добавлена поддержка внешних сред (Conda, Nix).

Использование внешних сред привело к ряду проблем:

- исчезла возможность получения полностью автономных AppImage и Apple Bundle;
- сборочное окружение стало проникать в итоговый пакет;
- стало сложно одновременно поставлять несколько независимых сборок FFmpeg;
- усложнилась работа с CUDA;
- усложнилось сопровождение пакетов для Linux, macOS и Windows.

Дополнительным фактором является необходимость одновременно поставлять несколько сборок FFmpeg внутри одного продукта.

Таким образом система должна перейти от модели внешних окружений к модели управляемых локальных toolchain.

---

# 3. Основные принципы

## 3.1. Локальная сборка

Все компоненты FFmpeg должны собираться на целевой системе.

Использование заранее собранных библиотек FFmpeg не предусматривается.

---

## 3.2. Постоянное хранение

Постоянному хранению подлежат только инструменты сборки:

- GCC;
- Rust;
- Cargo;
- Cargo-C;
- Meson;
- Ninja;
- CMake;
- прочие инструменты подготовки.

---

## 3.3. Отсутствие автоматических замен

Правила совместимости определяются разработчиком и фиксируются в реестрах.

Система не должна:

- самостоятельно оптимизировать выбор профилей;
- заменять один профиль другим;
- перестраивать логику совместимости на основании состава компонентов.

Поведение должно полностью определяться реестром.

---

## 3.4. Политика совместимости

Система реализует заранее определённые правила совместимости.

Она не является универсальным менеджером toolchain.

Каждый диапазон совместимости, версия инструмента и набор патчей считаются частью проекта и проходят отдельную проверку.

---

# 4. Архитектура профилей

Архитура состоит из двух уровней.

## 4.1. Верхний уровень

Верхний профиль определяет:

- целевую версию FFmpeg;
- целевую платформу;
- диапазон допустимых системных инструментов;
- правила выбора базового окружения.

Верхний профиль является политикой совместимости.

Пользователь не управляет его внутренними правилами.

---

### Поддерживаемые верхние профили

Первый этап должен содержать следующие профили:

```text
FFmpeg 8.1 + Linux
FFmpeg 9.0 + Linux

FFmpeg 8.1 + Windows
FFmpeg 9.0 + Windows

FFmpeg 8.1 + macOS
FFmpeg 9.0 + macOS
```

---

### Правила работы верхнего профиля

Верхний профиль задаёт диапазон допустимых версий инструмента.

Примеры:

```text
FFmpeg 8.1 + Linux
Допустимый диапазон:
GCC 12-13
```

```text
FFmpeg 9.0 + Linux
Допустимый диапазон:
GCC 15+
```

---

Если системный инструмент входит в допустимый диапазон профиля:

```text
должен использоваться системный инструмент
```

Развёртывание версии из локального хранилища в этом случае запрещается.

---

Если системный инструмент не удовлетворяет требованиям профиля:

```text
должна быть развернута версия,
определённая правилами профиля
```

Из локального хранилища.

---

### Профили macOS

Для macOS GCC не используется.

Система должна:

- проверять наличие поддерживаемой версии MacPorts Clang;
- использовать её при сборке;
- выдавать диагностическую ошибку при отсутствии подходящей версии.

Система не должна требовать наличие GCC на macOS.

---

## 4.2. Нижний уровень

Нижний профиль представляет требование конкретного компонента.

В отличие от верхнего профиля нижний профиль не использует диапазоны.

Он всегда ссылается на конкретную версию инструмента.

Примеры:

```text
gcc12
gcc13

rust-1.xx

cargo-c-x.xx
```

---

Компонент может содержать:

```yaml
toolchain: gcc12
```

или

```yaml
toolchain: rust
```

---

Если профиль указан:

- он обязан существовать в реестре;
- его архив обязан присутствовать в локальном хранилище;
- профиль обязан быть развёрнут.

---

Система не должна:

- подбирать альтернативный профиль;
- заменять профиль другой версией;
- выполнять автоматическое объединение профилей;
- изменять верхний профиль на основании нижнего.

---

# 5. Реестр компонентов

Каждый компонент получает поле:

```yaml
toolchain:
```

По умолчанию:

```yaml
toolchain: n/a
```

Это означает использование верхнего профиля.

---

Пример:

```yaml
rav1e:
  toolchain: rust

cuda:
  toolchain: gcc12

x264:
  toolchain: n/a
```

---

# 6. Хранилище инструментов

Все инструменты должны поставляться из локального хранилища.

Сетевые источники использовать запрещено.

---

Допускаются два способа поставки:

### Архив исходников

Инструмент собирается локально.

---

### Подготовленный бинарный архив

Инструмент разворачивается без пересборки.

---

Для каждого архива должны храниться:

- версия;
- контрольная сумма;
- сведения о патчах;
- сведения о платформе.

---

# 7. Постоянное хранилище

Рекомендуемая структура:

```text
toolchains/
├── profiles/
├── installed/
├── archives/
├── logs/
└── locks/
```

---

Постоянное хранилище должно содержать:

- подготовленные GCC;
- подготовленные Rust;
- Cargo;
- Cargo-C;
- прочие инструменты.

---

Постоянное хранилище не должно содержать:

- FFmpeg;
- x264;
- x265;
- rav1e;
- dav1d;
- libvmaf;
- другие библиотеки.

---

# 8. Планирование сборки

Перед началом сборки система должна:

1. определить версию FFmpeg;
2. определить платформенный профиль;
3. проверить совместимость системного окружения;
4. определить необходимые нижние профили;
5. проверить их наличие;
6. развернуть отсутствующие версии;
7. выполнить проверки;
8. начать сборку компонентов.

---

# 9. Политика совместимости

## FFmpeg 8.1

Подтверждённый диапазон:

```text
GCC 12-13
```

Если хост уже содержит:

```text
GCC 12
или
GCC 13
```

должен использоваться системный компилятор.

---

Если системный компилятор выходит за пределы диапазона:

```text
GCC 11
GCC 14
GCC 15
GCC 16
...
```

должен использоваться профиль, определённый правилами проекта.

---

## FFmpeg 9.0

Подтверждённый диапазон:

```text
GCC 15+
```

Подтверждены сборки с:

```text
GCC 15
GCC 16
```

---

Если системная версия входит в диапазон:

```text
должен использоваться системный компилятор
```

---

Если системная версия ниже диапазона:

```text
должен использоваться профиль проекта
```

---

# 10. GCC

Патчи для семейств:

```text
GCC 12/13
GCC 15/16
```

рассматриваются как часть проекта.

Версии проходят тестирование один раз и далее фиксируются.

Поведение системы не должно изменяться автоматически после появления новых версий GCC.

Изменение диапазонов совместимости допускается только через изменение реестра проекта.

---

# 11. Rust и rav1e

Поддержка rav1e является обязательной.

Если требуется Rust:

```text
система обязана развернуть профиль Rust
```

---

Если профиль отсутствует:

```text
сборка считается невозможной
```

Компонент не может автоматически исключаться из сборки.

---

# 12. CUDA

CUDA использует нижние профили.

Пример:

```text
CUDA 12.3
→ gcc12
```

```text
CUDA 13.1
→ gcc13
```

---

Если компонент запросил профиль:

```text
должна использоваться именно указанная версия
```

---

Подмена версии запрещается.

---

После подготовки профиля должны выполняться:

- проверка nvcc;
- проверка host compiler;
- проверка CUDA_NVCC_CCBIN.

---

# 13. Эффективное окружение

Все подсистемы должны использовать единый результат разрешения профилей:

- планировщик;
- определение платформы;
- FFmpeg policy;
- сборщики компонентов;
- CUDA;
- release bundle.

---

Не допускается ситуация, когда разные части системы используют разные компиляторы без явного указания профилей.

---

# 14. Очистка

Обычная очистка должна удалять:

- workspace;
- временные каталоги.

---

Не должны удаляться:

- GCC;
- Rust;
- Cargo;
- Cargo-C;
- Ninja;
- Meson;
- другие инструменты.

---

Очистка toolchain выполняется отдельной командой.

---

# 15. Офлайн режим

Офлайн режим запрещает любые сетевые операции.

Запрещены:

- Cargo download;
- Cargo install из сети;
- GitHub Release;
- pip download;
- любые фоновые загрузки.

---

Все файлы должны быть доступны локально до начала сборки.

---

# 16. CLI

CLI должен отображать:

- версию FFmpeg;
- платформенный профиль;
- диапазон совместимости профиля;
- системный инструмент;
- выбранный инструмент;
- нижние профили;
- состояние профилей;
- причины ошибок.

---

CLI должен поддерживать:

- просмотр плана;
- диагностику профилей;
- развёртывание профилей;
- удаление профилей;
- очистку workspace.

---

# 17. Критерии приёмки

Решение считается принятым при выполнении следующих условий:

- очистка workspace не затрагивает toolchain;
- системный инструмент используется при попадании в диапазон верхнего профиля;
- инструмент из хранилища используется только при отсутствии совместимого системного инструмента;
- верхние профили определяют диапазоны совместимости;
- нижние профили определяют конкретные версии;
- нижний профиль не может изменить верхний профиль;
- отсутствующий профиль разворачивается автоматически;
- отсутствующий архив вызывает диагностическую ошибку;
- rav1e является обязательным компонентом;
- CUDA использует строго указанные версии toolchain;
- инструменты используются из локального хранилища;
- офлайн режим исключает сетевые обращения;
- macOS использует MacPorts Clang;
- FFmpeg и его библиотеки всегда собираются заново;
- в постоянном хранилище находятся только инструменты подготовки и сборки;
- Nix более не требуется для функционирования системы.

---

# 18. Результат реализации

Должны быть реализованы:

- система верхних профилей совместимости;
- система нижних профилей инструментов;
- локальное хранилище архивов;
- постоянное хранилище инструментов;
- поддержка GCC 12/13;
- поддержка GCC 15/16;
- поддержка Rust/Cargo/Cargo-C;
- обновлённая логика CUDA;
- обновлённая система планирования;
- обновлённый CLI;
- обновлённые тесты;
- удаление зависимости от Nix.
