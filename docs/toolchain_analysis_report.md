# Постоянное окружение сборки и декларативные требования к toolchain

> Historical note (3.0): this report is the pre-implementation proposal that
> the toolchain store was built from. It is kept as a design record; the
> current behavior is documented in `DeveloperReadme.md` ("Toolchain store and
> provisioning"), `README.md` ("Toolchain Store"), and `CHANGELOG.md`. The
> `shell.nix` alternative it mentions was removed in 3.0.

## 1. Назначение и итог анализа

Отчет объединяет анализ репозитория и последующие уточнения требований.
Это предложение по развитию системы, а не описание уже реализованной функции.

**Идея реализуема:** инструменты и необходимые локальные зависимости можно
устанавливать в постоянный каталог вне workspace конкретной версии FFmpeg,
сохраняя их после очистки сборки. Существующие реестр, загрузчик, обработчики
сборки и механизмы обнаружения дают основу для реализации.

Однако одного переноса каталога недостаточно. Нужны декларативные требования
компонентов к toolchain, предварительное планирование недостающих окружений,
единый выбор инструментов и независимый учет постоянных установок.

Рекомендуемая последовательность:

**Выбрать компоненты → составить реестр необходимых toolchain → проверить
доступность → отметить недостающие для установки/сборки → подготовить и проверить
окружения → собрать компоненты.**

## 2. Требования с учетом замечаний

1. Версии компонентов остаются закрепленными конкретными архивами в Git LFS
   и метаданными реестра. Подготовка toolchain не должна незаметно обновлять их.
2. Каждый компонент получает поле `toolchain`, по умолчанию `n/a`.
3. `n/a` предлагается трактовать как отсутствие специального требования:
   компонент использует базовое окружение сборки. Это не означает, что ему
   не нужны компилятор или другие инструменты.
4. До сборки составляется дедуплицированный реестр необходимых toolchain,
   включая зависимости их подготовки.
5. Для каждого требования проверяются системные и ранее установленные
   локальные инструменты. Недоступные или несовместимые отмечаются для
   установки либо сборки из закрепленных источников.
6. Постоянные установки не удаляются при очистке workspace.
7. Требуется поддержать GCC 12/13 и согласованное окружение Rust/Cargo/cargo-c.
8. Для проектов пользователя нужен rav1e. Его нельзя молча исключать из
   результата из-за отсутствующего или устаревшего Rust; отказ от него должен
   быть явным решением пользователя.

Поле `toolchain` отсутствует в текущей модели компонента:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/components.py:67–102`.

## 3. Текущее состояние системы

### 3.1. Workspace и очистка

Workspace определяется версией FFmpeg. Распакованные исходники и состояние
сборки находятся внутри него:

- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/config.py:15–24,93–103`;
- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/app.py:64–71`.

Очистка удаляет активный workspace и старый каталог workspace целиком:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/app.py:325–358`.
Установленные туда инструменты удаляются вместе с результатами сборки.

### 3.2. Системные компоненты

Реестр поддерживает `system_component`, `system_tool_name`, `requires_tools`,
`depends_on`, платформенные переопределения и специальные обработчики.
Если системный компонент обнаружен, его сборка обычно пропускается; если
отсутствует — выполняется локальная сборка в workspace.

Основания:

- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/components.py:67–102`;
- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/builder.py:838–879`.

Но наличие инструмента сейчас не равнозначно пригодности его версии:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/builder.py:955–1035`.
Текущий механизм преимущественно решает задачу «собрать отсутствующее»,
а не «заменить несовместимое установленное».

Признак `system_component` объединяет инструменты и библиотеки: например,
Meson/Ninja/CMake, zlib, giflib и oneVPL. Автоматически переносить их все
в один общий prefix нельзя: библиотеки имеют дополнительные ограничения ABI.
Для giflib действует отдельное правило — при отсутствии внешнего системного
компонента сборщик выдает ошибку вместо локальной сборки:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/builder.py:819–836`.

### 3.3. Реестр и планирование

Текущий отбор учитывает инструменты, предоставляемые предыдущими компонентами,
но сохраняет порядок YAML. Некоторые компоненты исключаются из списка при
отсутствии `requires_tools`:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/components.py:358–424`.

Для нового порядка работы нужно сначала сохранить все выбранные компоненты
как потребителей требований, а затем планировать подготовку инструментов.
Иначе отсутствие toolchain скроет саму потребность в его установке.

Полноценное разрешение зависимостей подготовки toolchain, обнаружение циклов
и контроль успешности поставщиков инструментов потребуют отдельной логики.

### 3.4. Закрепленные источники

Архивы каталога источников отслеживаются Git LFS:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/.gitattributes:1`.
Версии, имена архивов и контрольные суммы задаются в реестре компонентов.
Загрузчик поддерживает локальные архивы, запрет сети и проверку SHA-256:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/downloader.py:95–125`.

Эту модель следует сохранить и распространить на артефакты toolchain.
Фиксация исходников при этом не гарантирует совместимость установленного
результата после смены архитектуры, backend или обновления ОС.

## 4. Применимость к исходным сценариям

### 4.1. Fedora 44, GCC 16 и FFmpeg 8.1

Локальный GCC 12/13 позволяет сформировать подходящее окружение без изменения
системного компилятора. Но добавления GCC в список компонентов недостаточно.

Текущая политика блокирует FFmpeg 8.1 по обнаруженным GCC/Clang до создания
сборщика. Наличие слишком нового Clang также отдельно влияет на решение:

- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/ffmpeg_policy.py:60–94`;
- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/app.py:95–127`.

Политику нужно применять к назначенному эффективному toolchain, сохраняя
пороги совместимости. Системный GCC должен оставаться характеристикой хоста,
а не автоматически определять компилятор каждого компонента.

Передача `CC`/`CXX` в FFmpeg уже поддерживается:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/builders/ffmpeg/ffmpeg.py:103–106`.
Выбор платформенной стратегии также должен учитывать эффективное окружение:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/platforms/resolver.py:18–36`.

Существующий Nix-путь использует `gcc13Stdenv` и предоставляет сборочные
зависимости:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/shell.nix:8–21`.
Его рекомендуется сохранить как альтернативу до практического подтверждения
нового механизма. В текущем `shell.nix` источник nixpkgs не закреплен, поэтому
строгая воспроизводимость всех версий этим файлом сама по себе не обеспечивается.

### 4.2. CUDA 12.6

В проекте уже есть проверка совместимости nvcc пробной компиляцией,
`CUDA_NVCC_CCBIN` и поиск альтернативного host-компилятора:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/platform_detect.py:810–928`.
Выбранный путь передается в сборку FFmpeg и libvmaf.

Постоянное хранилище GCC можно подключить к этому механизму. Проверку nvcc
нужно повторить после подготовки toolchain: начальное обнаружение выполняется
до установки недостающих инструментов.

Требование «CUDA 12.6 допускает только GCC 12» не подтверждено анализом
репозитория. GCC 12 можно выбрать как целевой профиль пользователя; пригодность
GCC 13 следует проверять по документации конкретного Toolkit и реальной сборкой.
Не следует подменять проверку отключением контроля версии компилятора.

Для первого рабочего профиля предпочтительно использовать согласованный GCC
для C/C++, библиотек и CUDA. Раздельные компиляторы требуют дополнительной
проверки ABI и runtime.

### 4.3. Ubuntu 24.04, Rust/Cargo и rav1e

В текущем реестре Rust нужен rav1e, а dav1d собирается через Meson:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/components.yaml:229–244,263–272`.

Обработчик Cargo требует Rust не ниже 1.95 из-за закрепленного cargo-c и
пропускает компонент при неподходящем Rust:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/builders/base.py:347–379`.

Следует подготовить согласованный закрепленный профиль Rust/Cargo/cargo-c,
изолировать его каталоги от пользовательского окружения и учитывать crates
для офлайн-работы. Сейчас `cargo install cargo-c` выполняется вне загрузчика
архивов и может обращаться к сети независимо от `allow_network_downloads`.

Конкретный состав пакетов Ubuntu и совместимость нового профиля в рамках
этого анализа не проверялись на реальной системе.

## 5. Предлагаемая архитектура

### 5.1. Декларативные требования

Разделить два реестра:

- **Компоненты:** закрепленные исходники, сборочные параметры и требуемый
  `toolchain`.
- **Toolchain:** идентификатор профиля, закрепленные артефакты, предоставляемые
  инструменты, допустимые платформы, зависимости подготовки, способ
  установки/сборки и критерии пригодности.

Поле компонента должно ссылаться на профиль, способный описать согласованный
набор инструментов, а не только одну команду. Это позволяет представить
Rust/Cargo/cargo-c и CUDA с host-компилятором без нескольких независимых
непроверенных настроек.

Требования могут различаться по закрепленной версии компонента и платформе.
Системные инструменты следует принимать только по явно определенным правилам:
точная версия либо разрешенный диапазон, комплектность и функциональная проверка.

### 5.2. Постоянное хранилище

Добавить конфигурируемый каталог вне очищаемых workspace. Разделить в нем:

- завершенные установки инструментов по версиям и платформам;
- профили окружения;
- сведения об установках и журналы;
- временные сборочные каталоги;
- при последующем расширении — совместимые наборы библиотек.

GCC 12 и GCC 13 должны сосуществовать без перезаписи общего prefix.
Инструменты нельзя подменять глобально в системе.

Необходимо отделить prefix установки от каталога исходников и workspace:
сейчас стандартные и специальные обработчики используют workspace напрямую:

- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/builders/base.py:70–95`;
- `/home/runner/work/ffmpeg_builder/ffmpeg_builder/builders/tools/ninja.py:31–34`.

### 5.3. Единое эффективное окружение

Обнаружение инструментов, планировщик, политика FFmpeg, CUDA-пробы и сборочные
команды должны использовать один результат разрешения toolchain.

Одного добавления постоянного каталога в PATH сборщика недостаточно:
часть проверок использует окружение процесса, тогда как команды выполняются
с отдельным окружением сборщика.

Для каждого компонента назначается собственное окружение. `n/a` использует
базовый профиль; специальные требования переопределяют необходимые инструменты.
При этом необходимо проверять совместимость с уже собранными зависимостями.

### 5.4. Учет и повторное использование

Постоянным установкам нужен независимый учет. Состояние FFmpeg не должно быть
источником истины о наличии toolchain.

Текущая проверка завершенности учитывает только имя, версию и статус:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/state.py:292–311`.

Для повторного использования требуются сведения об артефактах, платформе,
параметрах сборки и зависимостях, проверка реальных файлов и работоспособности,
межпроцессная блокировка и публикация только завершенной установки.
Нужно учитывать абсолютные пути, встроенные в установленные файлы:
произвольное перемещение готового prefix может нарушить работоспособность.

## 6. Порядок работы

1. Определить компоненты по версии FFmpeg, платформе и настройкам, не исключая
   их из-за отсутствующих инструментов.
2. Собрать и дедуплицировать требования `toolchain`.
3. Добавить зависимости подготовки toolchain; проверить циклы и наличие
   bootstrap-средств.
4. Проверить системные и постоянные локальные установки.
5. Показать, какие окружения пригодны, какие требуют установки/сборки,
   а какие недоступны с указанием причин.
6. Подготовить недостающие toolchain из закрепленных источников.
7. Проверить результат и назначить окружения компонентам.
8. Повторно оценить политику FFmpeg и возможности CUDA.
9. Собрать зависимости и FFmpeg, записав использованные профили в состояние.
10. При очистке удалить только workspace; очистку постоянных установок
    выполнять отдельно и явно.

Невозможность подготовить требуемый toolchain должна давать понятную ошибку,
а не автоматически превращать компонент в необязательный.

## 7. Риски и меры

| Риск | Рекомендация |
|---|---|
| Bootstrap GCC 12/13 на новом хосте | Специальный обработчик GCC с отдельным build-каталогом, учетом GMP/MPFR/MPC и проверкой bootstrap-компилятора и системных средств. |
| Загрязнение сборки инструментов флагами FFmpeg | Отдельное bootstrap-окружение без глобальных CUDA/include/static/native/OpenMP-флагов. |
| Смешивание C++ ABI, OpenMP и CUDA | Согласованные профили; учет libstdc++, libgcc и libgomp; проверки связанных компонентов. |
| Устаревшая установка после обновления ОС | Проверка платформы и работоспособности; возможность адресной переустановки без очистки всех инструментов. |
| Частичная установка и параллельный доступ | Блокировки, завершенные установки и независимый учет. |
| Случайное удаление постоянного каталога | Запрет пересечения путей с workspace, учет символических ссылок и отдельное подтверждение очистки. |
| Неполный офлайн-набор | Закрепленные архивы, зависимости bootstrap и crates; проверка SHA-256 и отказ от скрытых загрузок. |
| Непереносимый release | Расширение поиска runtime-зависимостей на постоянные prefix и проверка запуска без хранилища инструментов. |
| Перенос Linux-решения на другие backend | Первую реализацию ограничить Linux, явно различая native Linux и WSL2; MSYS2 и macOS рассматривать отдельно. |

Поиск runtime-зависимостей сейчас ориентируется главным образом на workspace
и некоторые платформенные каталоги:
`/home/runner/work/ffmpeg_builder/ffmpeg_builder/release_bundle.py:410–440`.

**Постоянный каталог не равен изоляции Nix:** остаются зависимости от системных
headers, libc, загрузчика и других средств. Не рекомендуется начинать с
локальной замены libc или графических драйверов.

## 8. Рекомендуемые этапы

1. Ввести поле `toolchain` и реестр профилей, сохранив поведение `n/a`.
2. Добавить предварительное планирование требований и диагностику недостающих
   инструментов без преждевременного исключения компонентов.
3. Разделить пути workspace и постоянных установок; добавить независимый учет
   и безопасную очистку.
4. Подключить единое эффективное окружение к обнаружению, сборке, UI,
   политике FFmpeg и CUDA.
5. Подготовить закрепленный профиль Rust/Cargo/cargo-c для rav1e.
6. Добавить специальные обработчики GCC 12/13 и проверить bootstrap.
7. После стабилизации расширить постоянное хранение на необходимые библиотеки
   с ключами совместимости и корректным учетом runtime-зависимостей.

Существующие инструменты можно использовать для проверки механизма постоянной
установки, но не следует автоматически переносить все `system_component`.

## 9. Проверки приемки

- Очистка workspace не затрагивает постоянные установки и их учет.
- Переключение версии FFmpeg повторно использует пригодный toolchain.
- Неподходящая системная версия отмечается для замены, несмотря на наличие команды.
- Компонент с недостающим toolchain остается в плане подготовки.
- `n/a` сохраняет использование базового окружения.
- Смена toolchain не переиспользует несовместимые библиотеки или результаты сборки.
- Поврежденные и незавершенные установки обнаруживаются.
- Параллельная подготовка одного toolchain не повреждает хранилище.
- Bootstrap-зависимости проверяются; циклы дают диагностируемую ошибку.
- Офлайн-режим не допускает скрытых загрузок Cargo или других установщиков.
- Отсутствие обязательного rav1e не маскируется успешным результатом.
- На целевых хостах проверяются C, C++, OpenMP, nvcc, сборка FFmpeg и rav1e.
- Release запускается без постоянного каталога инструментов либо явно
  документирует необходимые внешние runtime-зависимости.

Использовать существующие тесты для конфигурации, реестра, состояния,
workspace, обнаружения платформы, политик и обработчиков сборки.
Полная сборка на целевых системах нужна отдельно от модульных тестов.

## 11. Заключение и границы проверки

Рекомендуется развивать систему как **декларативное разрешение требований
компонентов к toolchain с постоянными локальными установками**.
Основной механизм — предварительный реестр потребностей и проверка доступности;
хранилище обеспечивает повторное использование после очистки workspace.

Приоритетные потребители — FFmpeg 8.1 на современных Linux-хостах, CUDA
с совместимым host-компилятором и rav1e с подходящим Rust/Cargo/cargo-c.
Nix следует сохранить как альтернативный путь.

Анализ выполнен по исходникам и существующим тестам репозитория. Реальная
сборка GCC, Rust, FFmpeg и CUDA на целевых системах не выполнялась.
Ограничения текущей политики проекта не являются самостоятельным доказательством
ограничений upstream-компонентов. Данные о конкретных дистрибутивах и Toolkit
требуют отдельной проверки. Изменение относится только к этому отчету,
поведение приложения не меняется.
