# Changelog

All notable changes to the FFmpeg Builder project.

## [2.0b0] - 2026-08-31

### Added

- **FFmpeg 9 integration beta** - Added selectable FFmpeg 9.0 source support while retaining FFmpeg 8.1 as the default. The macOS build using the default non-GPL configuration completed all 49 selected components: 37 source components and 12 system components, with no failures or skips. Generated `ffmpeg`, `ffprobe`, and `ffplay` binaries report FFmpeg 9.0.

### Fixed

- **FFmpeg 9 compatibility** - Fixed the macOS FFmpeg 9 build path: GMP static archives are PIC for nettle, libjxl thread probes link the C++ runtime, FFmpeg's Vulkan ffplay renderer receives its missing context header, and FFmpeg only enables libplacebo when it was built with Vulkan support.

### Known Limitations

- Linux and Windows MSYS2 UCRT64 FFmpeg 9 validation are pending before the stable 2.0 release.

## [Unreleased]

### Fixed

- **nv-codec-headers 13.1.x breaks FFmpeg 8.1 NVENC build (Windows MSYS2 UCRT64, 2026-09-05)** — `components.yaml` pinned `nv-codec` (the `ffnvcodec`/NVENC headers component) to `13.1.15.0`. FFmpeg 8.1's `libavcodec/nvenc.c`/`nvenc.h` compile-time feature checks are written against NVENC SDK **13.0** (`nvenc.h:104`, `#if NVENCAPI_CHECK_VERSION(13, 0)`), which assumes the SDK-13.0 layout of `NV_ENC_CLOCK_TIMESTAMP_SET`. SDK 13.1 restructured that struct, splitting the `countingType` bitfield into `countingTypeLSB`/`countingTypeMSB`, so `nvenc.c`'s `time_code->clockTimestamp[i].countingType = 0;` (in `nvenc_fill_time_code`) failed with `has no member named 'countingType'; did you mean 'countingTypeLSB'`, aborting the build with `make: *** [ffbuild/common.mak:91: libavcodec/nvenc.o] Error 1`. Root cause: the component registry advanced `nv-codec` past the newest SDK release without re-validating it against the pinned FFmpeg 8.1 source, which still targets the prior SDK generation. Fixed by re-pinning `nv-codec` to `13.0.19.0` (SHA-256 `13da39ed...242bee`, already present and Git LFS-tracked in `third_party/sources`, no network fetch required) — the last release whose `NV_ENC_CLOCK_TIMESTAMP_SET` layout matches what FFmpeg 8.1's `nvenc.c` expects. Verified: full Windows MSYS2 UCRT64 build completed successfully; the resulting `workspace/release/ffmpeg.exe` reports `--enable-cuvid --enable-nvdec --enable-nvenc --enable-ffnvcodec` and functional `h264_nvenc`/`hevc_nvenc`/`av1_nvenc`/`*_cuvid` codecs. Future refreshes of `nv-codec` past `13.0.x` must first confirm FFmpeg's targeted version has updated its `NVENCAPI_CHECK_VERSION` feature gates to SDK 13.1 (see `nvenc.h`) before bumping the pin; the `docs/ffmpeg_9.0_developer_readme.md` refresh-candidate note recommending `13.1.15.0` predates this finding and should be treated as unverified for the FFmpeg 8.1 build path.

- **`setup_windows_msys2_ucrt64.ps1` aborted on a fresh MSYS2 install before installing any packages (2026-09-05)** — The script ran a pre-flight `Invoke-MsysBash "which gcc; gcc -dumpmachine; which python; python -V"` before the `pacman -S` package-install step. `Invoke-MsysBash` treats any non-zero exit as fatal, so on a brand-new MSYS2 install (no `mingw-w64-ucrt-x86_64-toolchain` yet) `which gcc` failed and the script aborted immediately with a misleading "gcc not found" error, never reaching the step that actually installs gcc/cmake/ninja/meson/nasm/pkg-config. Separately, the post-install verification loop invoked `bash.exe` directly without first setting `$env:MSYSTEM = "UCRT64"` / `$env:CHERE_INVOKING = "1"`, so `/etc/profile` never added `/ucrt64/bin` to `PATH` — `which <tool>` reported every UCRT64 tool as missing even immediately after a successful `pacman -S --needed` install that showed all packages "up to date". Fixed by making the pre-flight check informational/non-fatal (diagnostic output only, does not throw) and by setting `MSYSTEM=UCRT64`/`CHERE_INVOKING=1` (restored afterward) around both the pre-flight check and the post-install tool verification loop. Verified: a fresh MSYS2 install now proceeds through `pacman -Syu`/`pacman -S`, and the post-install verification correctly reports `gcc`/`cmake`/`ninja`/`meson`/`nasm`/`pkg-config`/`python` as `OK` once installed.

### Fixed

- **gettext build fails on macOS with Apple clang 17 (GPL FFmpeg 9 path, 2026-08-31)** — Building `gettext` for the GPL crypto stack failed compiling gnulib's `libtextstyle/lib/iconv-ostream.c`: `configure`'s `AM_ICONV` check found Apple's system `iconv` "not working" (a known limitation of Apple's BSD-derived iconv vs. GNU iconv semantics) and set `HAVE_ICONV=0`, which selects gnulib's stub `iconv_ostream__flush` — a stub whose signature (missing the `ostream_flush_scope_t` parameter) does not match the `iconv_ostream_vtable` function-pointer slot, an upstream gnulib bug that only surfaces when the non-iconv branch is actually compiled. Apple clang 17 treats this as a hard `-Wincompatible-function-pointer-types` error (not merely a warning), aborting the build. Fixed by adding a `darwin` `configure_args_override` for `gettext` that swaps `--without-libiconv-prefix` for `--with-libiconv-prefix=/opt/local`, pointing configure at the MacPorts GNU libiconv already required for `macports-clang-17`; GNU libiconv passes the "working" check, so `HAVE_ICONV=1` and the buggy stub branch is never compiled. Verified: `am_cv_func_iconv_works=yes` in the libtextstyle `config.log`, `-liconv` now links cleanly with no `iconv-ostream.c` errors, and the resumed macOS FFmpeg 9 GPL build progressed `gettext` from `failed` to `completed` and continued into `openssl` and through to a full successful build (see above).

### Fixed

- **FFmpeg 9 skips Vulkan-disabled libplacebo (2026-08-31)** — FFmpeg's libplacebo integration uses Vulkan APIs. When `enable_libplacebo_vulkan: false`, the builder correctly compiled a software-only libplacebo archive, but still passed `--enable-libplacebo` to FFmpeg. FFmpeg 9 then compiled its Vulkan ffplay renderer against the headers and failed to link unavailable libplacebo Vulkan symbols. FFmpeg now omits `--enable-libplacebo` unless the configured libplacebo build has Vulkan enabled; standalone FFmpeg Vulkan remains enabled. Regression coverage verifies this configuration path.

- **FFmpeg 9 Vulkan ffplay renderer compilation (2026-08-31)** — FFmpeg 9's `fftools/ffplay_renderer.c` uses `AVVulkanDeviceContext` and `AVVulkanDeviceQueueFamily` when libplacebo/Vulkan rendering is enabled but omits `libavutil/hwcontext_vulkan.h`, which declares them. Builds failed with undeclared Vulkan context types after configure succeeded. The FFmpeg 9 build path now applies and verifies an idempotent source patch that adds the missing include before configure. Regression coverage verifies both the patch and its fail-fast behavior if a future FFmpeg source layout changes.

- **FFmpeg 9 static libjxl probe links the macOS C++ runtime (2026-08-31)** — `libjxl_threads.pc` omits its static C++ runtime dependency. FFmpeg 9 correctly finds the package but its configure probe failed on macOS with unresolved `std::__1` symbols because the builder supplied `-llcms2` without `-lc++`. The FFmpeg extra-library assembly now adds `-lc++` on macOS and `-lstdc++` elsewhere whenever libjxl is built. Regression coverage asserts the Darwin configure command includes both libjxl dependencies.

- **Nettle build links PIC GMP archives on macOS (2026-08-31)** — The non-GPL FFmpeg 9.0 build path selects GMP, nettle, and GnuTLS. Nettle builds helper executables that link the workspace `libgmp.a`; macOS rejected GMP's non-PIC assembly objects with `ld: Found illegal text-relocations`. GMP now receives its portable `--with-pic` configure option for every platform, producing static archives that can be linked into these executables. Regression coverage asserts the declarative GMP build option.

- **Installed package startup no longer misses `components.yaml` (2026-08-31)** — `components.yaml` is now declared as setuptools package data, so normal wheel installs place the declarative component registry beside `ffmpeg_builder.components`. This fixes `python -m ffmpeg_builder` failing at startup with `FileNotFoundError` when `ComponentRegistry` resolves its registry path. Regression coverage checks the package resource; verified by building a wheel, reinstalling it in `.venv`, and initializing the registry with all 63 components.

- **All mypy errors fixed; frozen baseline is now empty (2026-08-31)** — Fixed the entire pre-existing mypy baseline (34 errors, 26 unique), so `mypy_baseline.txt` is now empty and the baseline check guards a clean tree. Changes: (1) pinned type stubs `types-PyYAML` + `types-tqdm` added to `requirements-dev.txt` (CI installs it) — resolves the 3 `import-untyped` errors for yaml/tqdm; (2) typed the untyped defs: `main()` in `__main__.py`, `PlatformDetector.__init__` (also makes the `platform_info` attribute type visible, fixing the two `no-any-return` str errors), and the `shutil.rmtree` `onerror` callbacks in builder.py/app.py (matching the current typeshed signature, including the `sys.exc_info()` tuple form); (3) `BuildStepContext` Protocol attributes were `object` — now typed `CommandExecutor`/`StateManager`, fixing the 4 `attr-defined` errors in build_steps.py and the 3 `arg-type` errors where `FFmpegBuilder` is passed to `run_step`/`run_make`/`run_install`; (4) `run_make`/`_run_make` `jobs` narrowed from `Union[str, int]` to `int` (matches `execute_make`; all callers pass the int from `get_num_jobs`); (5) Windows-only `ctypes.windll` usage is now inside `sys.platform` guards (mypy narrows these) plus an explicit `float()` conversion; (6) the `vainfo` subprocess result was renamed to avoid a `CompletedProcess[bytes]`/`[str]` reassignment conflict in `_check_qsv`; (7) `ToolInfo.version`/`.path` are `str | None` — compiler-info dicts now use `or "Unknown"`; (8) downloader: the `add_done_callback` lambda replaced with `functools.partial`, `on_progress` captured locally for the closure (mypy does not narrow attribute access inside nested functions), and `filename` annotated `str`; (9) the `platform_overrides` YAML value is passed as `data.get(...) or {}`. Verified: pytest 136 passed / 2 skipped, `black --check` clean, mypy 0 errors.

- **macOS release bundle is now relocatable (M8, 2026-08-31)** — Production-readiness review, step 6. `make_release_bundle()` copied dylibs next to the binaries but never rewrote install names/rpaths, so the "redistributable" bundle only ran on machines where the build-time absolute paths (workspace/lib, /opt/local/lib/libomp, /usr/local/lib) still existed. On macOS the bundle now gets a relocatability pass after copying: references to *bundled* dylibs (resolved via the existing dependency-resolution logic, so only files actually copied into the bundle are touched — system libraries keep their original references) are rewritten to `@rpath/<name>` with `install_name_tool -change`; each bundled dylib's own install name is set to `@rpath/<name>` (`-id`); `@loader_path` is added as an rpath to every Mach-O file in the bundle (`-add_rpath`, skipped when already present); and each modified file is re-signed ad-hoc (`codesign --force -s -`) because install_name_tool invalidates the signature and Apple Silicon refuses to load a Mach-O with an invalid signature. The rewrites are recorded in a new `install_name_rewrites` manifest field. Two collector bugs found while verifying were also fixed: (1) `otool -L` lists a dylib's own install name as the first entry, which was treated as a regular reference — self-references are now skipped (the id is handled by `-id`); (2) on modern macOS, system references (`/usr/lib/*`, `/System/Library/*`) resolve from the dyld shared cache where the literal path does not exist on disk, so a healthy build reported ~20 false `missing_dependencies` — verified on the real built `workspace/bin/ffmpeg`: 23 dylibs collected, 0 missing after the fix. New test: a scripted-otool darwin bundle verifies the -change/-id/-add_rpath/codesign calls, self-reference skipping, system references not reported missing, and genuinely missing dylibs still reported. Verified end-to-end with a real clang-compiled dylib + executable (absolute install name + absolute rpath, mirroring a real build): the bundle runs in place and after being moved to a different path. **Follow-up (found while verifying a real full build):** with a symlinked install name (MacPorts-style, e.g. `/opt/local/lib/libxcb.1.dylib` → `libxcb.1.1.0.dylib`) the @rpath target used the *link* name while the bundle copies the file under its resolved (symlink-followed) name, so dyld could not load the bundle. Rewrites now target the resolved file name (the self-reference check compares resolved names too); the unit test uses a symlinked dylib to cover this. Re-verified against the real full build: the regenerated `workspace/release` bundle loads and encodes (libx264/libvpx/libsvtav1/libopus) both in place and from a relocated path, with `missing_binaries`/`missing_dependencies` empty.

- **CI added; formatting/mypy baseline frozen (L10, 2026-08-31)** — Production-readiness review, step 5. No CI workflow existed, so `black`/`mypy` versions drifted between machines and the baseline quietly changed. Four changes: (1) `requirements-dev.txt` pins the exact dev tool versions (pytest 9.1.1, black 26.5.1, mypy 2.3.1); CI and local dev install the same set, and bumping a pin requires re-running `black .` and refreshing the mypy baseline in the same commit. (2) The repo was formatted with an older black; the pinned 26.5.1 re-wrapped long lambda/call lines in 3 files (`component_builders.py`, `release_bundle.py`, `tests/test_builder_split.py`), so `black --check .` now passes on the pinned version. (3) `scripts/check_mypy_baseline.py` + `mypy_baseline.txt` freeze the pre-existing mypy baseline (34 errors, 26 unique after normalisation): the script runs the pinned mypy on the project source (top-level modules + `ui/`, never `.` so `workspace/` is never crawled), strips line numbers and collapses duplicates, and fails only on errors missing from the baseline — a ratchet where fixing errors is always green and adding errors is red; `--update` refreshes the baseline deliberately. (4) `.github/workflows/ci.yml` runs pytest + `black --check .` + the mypy baseline on push to `master` and on PRs (ubuntu-latest, Python 3.12). Verified end-to-end against a fresh clone with a clean venv (LFS pointers, no `workspace/`): all three steps green. Supporting fix: the sha256-mirror test now skips un-pulled Git-LFS pointer files in `third_party/sources` (a CI checkout without `git lfs pull` would otherwise hash pointer files and report false mismatches) — real archives are still verified, and CI no longer needs a ~1 GB `git lfs pull`.

- **`curl` removed from required/detected tools (M9, 2026-08-31)** — Production-readiness review, step 4. The downloader fetches archives via `requests`, and no code path in the source invokes `curl`, yet `curl` was listed in `SystemReport.get_missing_required_tools()` and detected by `PlatformDetector._detect_tools()`. Systems without curl therefore got a false "missing required tool" report on the start screen. Removed from both lists. New tests: the required-tools list (Linux and macOS variants) no longer contains curl, and `_detect_tools()` no longer produces a curl entry.

- **`cargo-c` install is now version-pinned (M6, 2026-08-31)** — Production-readiness review, step 4. `_build_cargo()` ran a bare `cargo install cargo-c`, which installed the *latest* crates.io release at build time: a reproducibility gap (two machines building on different days could get different cargo-c), a network dependency even in offline-first mode, and a from-source compile (~1–2 min) on every machine. The install is now `cargo install cargo-c --version 0.10.25`, with the version in a module-level `CARGO_C_VERSION` constant to bump deliberately when a new release is validated. New test: the install command carries the pinned version and the subsequent `cargo cinstall` step still runs.

- **Project-relative paths are now anchored to the project root (M5, 2026-08-31)** — Production-readiness review, step 4. The launcher and app resolved `workspace/`, `build_config.yaml`, and `source_archives_dir: third_party/sources` relative to the *current working directory*, while `ComponentRegistry` already anchored `components.yaml` to its module file. Running `ffmpeg_builder` from any directory other than the repository root therefore silently used a different workspace/config/archive location, breaking the offline-first archive lookup with a confusing error. All project-relative defaults are now anchored to a per-module `PROJECT_ROOT` (`Path(__file__).resolve().parent` — the package is the repository root itself in the flat layout): `__main__.py` (workspace), `app.py` (workspace + config path), the `ConfigManager` default config path (`config.py`), the `StateManager` default state path (`state.py`), and `FFmpegBuilder.source_archives` (`builder.py`) — a relative `source_archives_dir` resolves against the project root, an absolute one is honoured as-is. Explicitly passed paths (e.g. `FFmpegBuilderApp(workspace=...)`, test fixtures) are unchanged. New tests: default config path, default state path, relative archive-dir anchoring, and absolute archive-dir pass-through — each verified with `monkeypatch.chdir` into a temp CWD.

- **Source patches now verify they took effect (M7, 2026-08-31)** — Production-readiness review, step 3. Six version-specific source patches used `content.replace(...)` without asserting the replacement happened, so a component version bump in `components.yaml` would silently stop applying the patch and surface later as an obscure compile/link failure. Each patch site now verifies its post-patch state and raises a `BuildError` naming the file, the expected marker, and "the component version may have changed": xvidcore `encoder.h` (unguarded C23 `typedef int bool;` must be gone), x265 `json11.cpp` (`#include <cstdint>` must be present — catches the anchor `#include <limits>` moving), x265 `.pc` (`-lgcc_s` removed for full_static), libvpx darwin `Makefile` (both link-flag rewrites removed), libvorbis `configure.ac` (`-force_cpusubtype_ALL` removed), libjxl `deps.sh` (realpath call must be guarded when realpath is missing), libzmq `proxy.cpp` (old `stats_proxy` initializer removed), and openssl `configdata.pm` (`-std=c11` replaced with `-std=gnu11`). Two shared helpers `_assert_patch_absent()` / `_assert_patch_present()` implement the check; the existing `_patch_libplacebo_glslang_search` already followed this standard and is unchanged. The libjxl patch trigger also became idempotent (skips when the guard is already present). New tests: both helpers (pass + raise), and `build_x265` end-to-end — fails fast with the clear message when the json11 anchor is missing, and inserts the include at the right position when it is present.

- **Deleted dead `build_all()` orchestration loop (H3, 2026-08-31)** — Production-readiness review, step 3. `FFmpegBuilder.build_all()` was never called (the real build loop is `FFmpegBuilderApp._run_build()`) and had already diverged from it: it did not handle `SkipComponent` (would propagate unhandled), marked components `COMPLETED` unconditionally — overwriting the `SYSTEM` status that `build_component()` sets for system-provided components — and had no retry/skip/abort flow. A second, stale copy of the build loop in a build engine is an invitation to future divergence, so it was deleted along with its now-unused `tqdm` import (downloader.py still uses tqdm, so the dependency stays). This also removes one pre-existing mypy finding (missing tqdm stubs), dropping the baseline from 34 to 33 errors. New test: guard asserting `build_all` stays deleted.

- **State file is now crash-safe and forward-compatible (M4, 2026-08-31)** — Production-readiness review, step 2. Three robustness gaps in `state.py`: (1) `BuildState.from_dict()` passed the whole payload to the dataclass constructor, so any unknown top-level key (e.g. a state file written by a newer version) raised `TypeError` and made the app unusable; unknown keys are now ignored, matching the pattern `BuildConfig.from_dict()` already used. (2) A corrupt component entry (missing/unknown `status`, non-dict value) raised `KeyError`/`ValueError` on load; such entries now reset to `PENDING` so the component is rebuilt. (3) `StateManager.save()` wrote the state file in place, so a crash mid-write left a truncated `build_state.json` that crashed `load()` on every subsequent start (the app reads it on every loop iteration, so the app was unusable until the file was manually deleted); saves are now atomic (write to a per-PID temp file + `os.replace`, temp cleaned up on failure), and `load()` treats an unreadable file as "no previous build" with a logged warning instead of raising. New tests: unknown top-level keys, unknown/missing/non-dict component entries, corrupt-JSON load returning None (with warning), valid load still working, and no temp-file leftovers after save.

- **Config input validated; `get_num_jobs` no longer crashes on bad values (M3, 2026-08-31)** — Production-readiness review, step 2. Two crash paths: (1) `ConfigScreen` stored the jobs prompt verbatim and did `int(workers)` on the workers prompt — a non-numeric answer raised `ValueError` caught only by the top-level handler, killing the app with "Fatal error"; (2) `get_num_jobs()` did a bare `int(config_num_jobs)`, so a hand-edited `build_config.yaml` with `num_jobs: abc` crashed at build start (outside the try block), and `num_jobs: 0` produced `make -j0` (unlimited parallelism). `ConfigScreen` now re-prompts until the jobs value is `auto` or a positive integer and the workers value is a positive integer (new `_parse_positive_int()` helper); `get_num_jobs()` is the defensive backstop for hand-edited configs — invalid or non-positive values fall back to the auto-detected core count (minimum 1) instead of raising. - **Release bundle no longer fails on fully-static builds (M2, 2026-08-31)** — Production-readiness review, step 2. `make_release_bundle()` ran `ldd` on every Linux binary and raised `BuildError` on any non-zero exit. - **CUDA compute capability now uses numeric minimum (M1, 2026-08-31)** — Production-readiness review, step 2. `_detect_cuda_compute_capability()` compared nvidia-smi compute-capability strings lexicographically (`min(["86", "120"]) == "120"`), so on a mixed-generation GPU system (e.g. sm_86 Ampere + sm_120 Blackwell) `--nvccflags=-gencode arch=compute_120` was emitted and the resulting FFmpeg binary could not run on the older GPU. - **Archive integrity enforced for network downloads (H1, 2026-08-31)** — Production-readiness review, step 1. The sha256 verification infrastructure in `downloader.py` existed but was dead code: no component in `components.yaml` declared a checksum, so with `allow_network_downloads=true` a corrupt or tampered archive (especially via the plain-HTTP `ftp.osuosl.org`/Xiph fallbacks) would be extracted and built with no detection. Two changes: (1) populated `sha256` for all 63 components, computed from the verified local source mirror (`third_party/sources`) and checked against it by a new test; (2) added a `require_sha256_for_network` policy (default `True`, exposed as `BuildConfig.require_sha256_for_network` and wired through `FFmpegBuilder` into the downloader) that refuses to fetch an archive over the network unless a sha256 is supplied, failing fast instead of downloading something that cannot be verified. New tests: refuse unverified network download, allow verified network download, policy-disable path, unverified-local-with-warning, well-formed sha256 for every registry component, and hash agreement with the mirror.

- **`get_buildable()` is now tool-aware (H2, 2026-08-31)** — Production-readiness review, step 1. `get_buildable()` previously gated `requires_tools` against pre-build *system* tools only. ## [1.0.6] — 2026-07-19

### Fixed

- **svtav1 on GCC 16 / glibc 2.43** — SVT-AV1 4.0.1 includes `<sched.h>`/`<pthread.h>` from a project header (`Source/Lib/Codec/svt_threads.h`) and defines `_GNU_SOURCE` there. On modern glibc this is ignored when the translation unit is compiled with `-std=c11` because GCC defines `__STRICT_ANSI__`, which hides GNU/POSIX extensions (`locale_t`, `clockid_t`, `posix_memalign`, `strcasecmp`, etc.). Added a Linux `platform_overrides` entry that appends `-std=gnu11` to svtav1 CFLAGS, mirroring the existing `gettext` workaround. The same override is what the original `build-ffmpeg` script relies on
- **Out-of-sync default C standard** — `ffmpeg_builder/build_config.yaml` still set `linux.c_standard: c11` despite the documented default in `profiles/default.yaml` and the [1.0.5] release notes already declaring `gnu11` as the default. The runtime state file (`workspace/build_state.json`) inherited the stale `c11` value, which is why the failing build used `-std=c11`. Synced `build_config.yaml` to `gnu11` so a fresh checkout also gets the working default
- **x265 on GCC 15/16 / libstdc++** — `source/dynamicHDR10/json11/json11.cpp` uses `uint8_t` but only includes `<limits>`. Starting with libstdc++ shipped in GCC 15, `<limits>` no longer transitively pulls in `<cstdint>`, so `uint8_t` is undeclared and the 12-bit x265 build fails. Added a source patch in `build_x265()` that injects `#include <cstdint>` right after `<limits>`, matching the `sed -i '23a #include <cstdint>'` line from the original `build-ffmpeg` script
- **FFmpeg configure: `libjxl_threads >= 0.7.0 not found`** — libjxl 0.11.2 ships a `libjxl_threads.pc` that omits `-lstdc++` from `Libs`/`Libs.private`, so FFmpeg's `require_pkg_config` link test fails with undefined references to `std::condition_variable`/`operator new`. Added `-lstdc++` to `extralibs` whenever `libjxl` is in the build set (Linux only; macOS already uses `-lc++` via the `libvmaf` branch). libjxl itself is a C++ library and the C++ runtime is needed for the threads runner even though the pkg-config file does not declare it
- **FFmpeg configure: `SvtAv1Enc >= 0.9.0 not found` and vid.stab link error** — On Fedora/RHEL-family distributions, CMake's default `CMAKE_INSTALL_LIBDIR` is `lib64`, so SVT-AV1 4.0.1 and vid.stab install their libraries and pkg-config files to `<workspace>/lib64/` and `<workspace>/lib64/pkgconfig/`, but the builder only searched `<workspace>/lib/`. Added `<workspace>/lib64/pkgconfig` to `PKG_CONFIG_PATH` and `<workspace>/lib64` to `LDFLAGS` so FFmpeg's `require_pkg_config` resolves `SvtAv1Enc.pc` and the linker finds `libSvtAv1Enc.a` and `libvidstab.a`

### Notes

- **Target environment** — Debugging performed on Fedora Linux 44, dual AMD Instinct MI50, dual Intel Xeon Broadwell, GCC 16.1.1, glibc 2.43, Python 3.14. The svtav1 and x265 failures reproduce deterministically on this environment and are fixed by the changes above
- **Successful Fedora 44 build** — Full FFmpeg 8.1 build (45/57 components, 12 LV2/OpenCL/AMF/VapourSynth-system items skipped on this environment) completed end-to-end on Fedora Linux 44 with GCC 16.1.1 and glibc 2.43. The resulting `ffmpeg` binary statically links `libsvtav1`, `libx264`, `libx265` (multi-bitdepth), `libaom`, `libdav1d`, `libjxl`, `libfdk_aac`, `libvpx`, `libmp3lame`, `libopus`, `libvorbis`, `libtheora`, `libsrt`, `libzmq`, `librav1e`, `libvmaf`, `libwebp`, `libfreetype`, `vid.stab`, `libssl`, `libcrypto`, `libsdl`, `libzmq`, `libopencore-amrnb/wb`, and all GPL/non-free codecs enabled. The build is the first verified run on this exact hardware (AMD Instinct MI50 + Intel Xeon Broadwell, Fedora 44)

- **Platform override application** — Fixed `get_build_env()` condition from `component.name in component.platform_overrides` to `self.platform in component.platform_overrides`. Previously overrides (including the `gettext` `-std=gnu11` fix) were never applied
- **OpenSSL on GCC 16** — OpenSSL `./Configure` forces `-std=c11` on x86_64, which breaks GCC 16's inline-assembly handling in `crypto/bn/asm/x86_64-gcc.c`. Added a post-configure patch that replaces `-std=c11` with `-std=gnu11` in `Makefile` and `configdata.pm`
